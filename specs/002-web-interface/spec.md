# Feature Specification: Веб-интерфейс помощника поддержки МИСИС

**Feature Branch**: `[002-web-interface]`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "Веб-фронт для ИИ-помощника техподдержки МИСИС (ядро — фича 001): вход на сайте в самом начале работы (профиль пользователя), форма подачи обращения с диалогом уточнений, личный кабинет (мои обращения, заказ справок из каталога, статусы заказов), админка оператора (очередь, эскалации с саммари, статус-борд сервисов, раздел заказов справок, тест-панель инструментов, метрики, действия «в базу знаний» и «уведомить затронутых»)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вход в начале работы (Priority: P1)

Пользователь открывает сайт и в первую очередь авторизуется (эмуляция: ввод email МИСИС, без внешнего IdP). После входа система знает профиль (ФИО, группа/роль, email) — все обращения и заказы справок автоматически привязаны к нему: «по мне была инфа». Сессия переживает перезагрузку страницы.

**Why this priority**: Без идентификации не работают заказ справок, дедупликация и персонализация — это входная точка всего веб-опыта.

**Independent Test**: Открыть сайт → экран входа → ввести email `@misis.ru` → попасть в интерфейс с видимым профилем; перезагрузить → сессия на месте.

**Acceptance Scenarios**:

1. **Given** неавторизованный посетитель, **When** открывает сайт, **Then** видит экран входа, форма подачи недоступна до авторизации.
2. **Given** введён email с доменом `@misis.ru`/`@edu.misis.ru`, **When** вход выполнен, **Then** показан профиль (ФИО, группа/роль, email).
3. **Given** введён email с чужим доменом, **When** попытка входа, **Then** отказ с подсказкой о корпоративной почте.

---

### User Story 2 - Подача обращения и диалог с агентом (Priority: P1)

Авторизованный пользователь вставляет письмо или расшифровку разговора в форму. На экране появляется результат разбора: маршрут (значок: авто-проверка / база знаний / заказ справки / оператор), приоритет, обоснование, подзадачи. Если задан уточняющий вопрос — диалог продолжается в том же окне. Извещение о сбое оформлено отдельно и заметно. Есть кнопки готовых примеров обращений для демо.

**Why this priority**: Основной пользовательский сценарий и лицо продукта на демо.

**Independent Test**: Войти → вставить пример «не работает Wi-Fi» → увидеть маршрут, ответ/извещение; ответить на уточняющий вопрос в том же окне.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** отправлено обращение, **Then** показаны маршрут, приоритет, обоснование и результат действия.
2. **Given** агент задал уточняющий вопрос, **When** пользователь отвечает, **Then** разбор продолжается в том же окне без потери контекста.
3. **Given** подтверждённый сбой, **When** результат показан, **Then** извещение визуально отличается (заметный блок «сбой известен, работы ведутся»).

---

### User Story 3 - Личный кабинет: обращения и заказ справок (Priority: P2)

Пользователь видит свои обращения со статусами. Отдельный раздел — заказ справок: каталог из 5 типов с описаниями (о выплатах; справка-вызов; для переболевших/медотвода/вакцинации; с места учёбы; в военкомат), кнопка заказа и список своих заказов со статусами: «не обработана», «обрабатывается», «готова и ждёт выдачи», «забрана». Заказ возможен и через диалог с агентом — он появляется в том же списке.

**Why this priority**: Прикладная ценность для студента и наглядный end-to-end сценарий со статусами.

**Independent Test**: Заказать справку с места учёбы из каталога → заказ в списке со статусом «не обработана»; после смены статуса оператором — статус обновился у пользователя.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** открывает каталог, **Then** видит 5 типов справок с описаниями и кнопкой заказа.
2. **Given** заказ создан (из каталога или через агента), **When** пользователь открывает «мои заказы», **Then** виден заказ с актуальным статусом из четырёх.

---

### User Story 4 - Админка оператора (Priority: P2)

Оператор открывает админку: очередь обращений (приоритет, маршрут, обоснование, канал, статус), статус-борд сервисов (сайт, LMS, три Wi-Fi сети), баннер активного инцидента. Карточка эскалации оформлена «красиво»: саммари сути, результаты автопроверок, рекомендуемый шаг, исходный текст с переводом, журнал действий. Действия оператора: закрыть эскалацию, «в базу знаний» (с LLM-черновиком статьи), «уведомить затронутых» при инциденте.

**Why this priority**: Рабочее место оператора — главный экран демо после формы подачи.

**Independent Test**: Создать эскалацию → открыть админку → саммари понятно без чтения исходника ≤ 30 сек; закрыть с добавлением в базу знаний.

**Acceptance Scenarios**:

1. **Given** эскалированное обращение, **When** оператор открывает карточку, **Then** видны саммари, проверки, рекомендация, исходник, перевод и журнал.
2. **Given** активный инцидент, **When** оператор в админке, **Then** виден баннер инцидента и кнопка «уведомить затронутых».
3. **Given** закрытая эскалация, **When** оператор нажимает «в базу знаний», **Then** показан черновик статьи для подтверждения.

---

### User Story 5 - Админка: раздел заказов справок (Priority: P2)

Отдельный раздел админки для заказов справок: список всех заказов (тип, заявитель, время, статус), смена статуса по цепочке «не обработана» → «обрабатывается» → «готова и ждёт выдачи» → «забрана». Пользователь сразу видит смену статуса в кабинете.

**Why this priority**: Заказанный «прикол на админке для заказов справки» — без смены статусов кабинет пользователя мёртв.

**Independent Test**: Заказ пользователя появляется в разделе → оператор двигает статус → пользователь видит обновление.

**Acceptance Scenarios**:

1. **Given** новый заказ, **When** оператор открывает раздел заказов, **Then** заказ виден с типом, заявителем и статусом «не обработана».
2. **Given** заказ в работе, **When** оператор меняет статус, **Then** новый статус виден пользователю в кабинете.

---

### User Story 6 - Тест-панель инструментов (Priority: P3)

Вкладка админки «Инструменты»: кнопки запуска exec-инструментов с живым выводом (проверить сайт, проверить LMS, проверить Wi-Fi сеть), переключатели состояния Wi-Fi сетей (норма/сбой), кнопка «симулировать волну из 3 однотипных жалоб». Используется для теста и как демо-пульт на сцене.

**Why this priority**: Без неё детектор инцидентов и ветку «сбой» не показать вживую; утверждена заказчиком.

**Independent Test**: Нажать «проверить сайт» → вывод кода и времени отклика; переключить MISIS-EDU в «сбой» → статус-борд покраснел; «волна жалоб» → инцидент.

**Acceptance Scenarios**:

1. **Given** вкладка «Инструменты», **When** нажата кнопка проверки, **Then** показан результат вызова инструмента.
2. **Given** переключатель Wi-Fi в «сбой», **When** приходит жалоба на эту сеть, **Then** пользователь получает извещение о сбое.

---

### User Story 7 - Метрики в админке (Priority: P3)

Виджет метрик: % обращений, закрытых без человека; среднее время первой реакции; число инцидентов. Цифры для питча.

**Why this priority**: Приятный финальный штрих админки, строится на готовых данных журнала.

**Independent Test**: После серии обращений виджет показывает ненулевые значения, согласованные с журналом.

**Acceptance Scenarios**:

1. **Given** обработано несколько обращений, **When** открыт виджет, **Then** метрики соответствуют журналу действий.

---

### Edge Cases

- Неавторизованный доступ к кабинете/админке → перенаправление на вход (админка — отдельный вход или явный вход «как оператор»).
- Потеря сессии посреди диалога → после повторного входа обращение сохранено.
- Сервис недоступен в момент проверки с тест-панели → честный вывод ошибки инструмента.
- Долгий ответ ядра → индикатор обработки, без «зависшего» экрана.

## Requirements *(mandatory)*

### Functional Requirements

**Авторизация и профиль**

- **FR-001**: Сайт MUST требовать вход в самом начале работы, до подачи обращений (эмуляция: email с доменом `@misis.ru`/`@edu.misis.ru`).
- **FR-002**: После входа MUST отображаться профиль (ФИО, группа/роль, email); профиль привязывается ко всем обращениям и заказам.
- **FR-003**: Сессия MUST сохраняться при перезагрузке страницы.

**Подача и диалог**

- **FR-010**: Форма подачи обращения MUST принимать текст письма или расшифровки разговора.
- **FR-011**: Результат разбора MUST показывать: маршрут с обозначением типа, приоритет, обоснование маршрута, список подзадач.
- **FR-012**: Уточняющий диалог MUST вестись в том же окне без потери контекста.
- **FR-013**: Извещение о подтверждённом сбое MUST иметь отдельное заметное оформление.
- **FR-014**: MUST быть кнопки готовых примеров обращений (демо-режим): сайт, LMS, Wi-Fi, неполное письмо, несколько вопросов, расшифровка звонка, справка, мат/английский.

**Личный кабинет**

- **FR-020**: Кабинет MUST показывать обращения пользователя со статусами.
- **FR-021**: Каталог справок MUST показывать 5 типов с описаниями и кнопкой заказа.
- **FR-022**: Список «мои заказы» MUST показывать актуальный статус каждого заказа (4 статуса из ядра).

**Админка**

- **FR-030**: Очередь обращений MUST показывать приоритет, маршрут, обоснование, канал, статус.
- **FR-031**: Карточка эскалации MUST содержать саммари, результаты автопроверок, рекомендацию, исходник с переводом, журнал.
- **FR-032**: Статус-борд MUST показывать состояние сайта, LMS и трёх Wi-Fi сетей.
- **FR-033**: Раздел заказов справок MUST показывать все заказы и позволять смену статуса по цепочке.
- **FR-034**: Тест-панель MUST позволять запускать exec-инструменты с выводом, переключать состояние Wi-Fi сетей, симулировать волну из 3 однотипных жалоб.
- **FR-035**: Виджет метрик MUST показывать: % обращений без человека, среднее время первой реакции, число инцидентов.
- **FR-036**: Действия оператора MUST включать: закрытие эскалации, «в базу знаний» с подтверждением черновика, «уведомить затронутых» при инциденте.
- **FR-037**: При активном инциденте MUST показываться баннер в админке.

### Key Entities

- **Сессия**: токен, профиль, время входа.
- **Профиль пользователя**: ФИО, группа/роль, email (тестовые данные).
- **Представления**: экран входа, форма+диалог, кабинет, админка (очередь, эскалация, заказы, статус-борд, инструменты, метрики).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полный демо-цикл (вход → обращение → результат → действие оператора) показывается на экране ≤ 2 минут без перезагрузок и ручного вмешательства в данные.
- **SC-002**: Оператор понимает ситуацию по карточке эскалации ≤ 30 секунд (без чтения исходника).
- **SC-003**: Все демо-сценарии запускаются с тест-панели или кнопками примеров в один клик (0 ручной подготовки данных на сцене).
- **SC-004**: Заказ справки end-to-end (каталог → заказ → смена статуса оператором → статус у пользователя) выполняется ≤ 1 минуты.
- **SC-005**: 100% пользовательских действий доступны только после входа; 0 обращений без привязки к профилю.

## Assumptions

- Авторизация эмулируется: тестовые профили, проверка домена email, без реальных паролей и внешнего IdP.
- Админка — отдельный вход «как оператор» в том же приложении, без ролевой модели (один оператор).
- Вся логика и данные — из ядра (фича 001); фронт — тонкий клиент.
- Telegram-канал — фича 003; его обращения отображаются в админке с пометкой канала.
- Стилистика — тёмная тема существующего scaffold'а; без дизайн-системы и сложной вёрстки (хакатон).
