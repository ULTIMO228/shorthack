## User Scenarios & Testing *(mandatory)*

### User Story 1 - Автоматический разбор и маршрутизация обращения (Priority: P1)

Пользователь пишет в поддержку свободным текстом: своими словами, возможно с матом, на любом языке, с несколькими вопросами сразу. Работать можно и без почты МИСИС (гость): система ведёт гостевую сессию и выполняет анализ в полном объёме; персональные возможности (заказ справок, кабинет, статусы заказов) требуют входа по корпоративной почте. Система привязывает обращение к профилю или гостевой сессии, нормализует текст (маскирует ненормативную лексику, определяет язык), разбивает составное обращение на атомарные подзадачи, классифицирует каждую языковой моделью в маршрут — автоматическая проверка / ответ из базы знаний / заказ справки / эскалация оператору — и присваивает приоритет с обоснованием. Повторное обращение по той же теме привязывается к открытой заявке, а не плодит новую.

**Why this priority**: Ядро продукта и обязательный минимум хакатона: принять обращение, понять его через LLM, выбрать и выполнить действие.

**Independent Test**: Отправить три контрольных обращения (простое, составное, с матом/на английском) и проверить маршруты, приоритеты, обоснования; отправить дубль и убедиться в склейке с открытой заявкой.

**Acceptance Scenarios**:

1. **Given** обращение «Не могу войти в LMS», **When** отправлено, **Then** классифицировано (категория, маршрут, приоритет) и показано обоснование маршрута.
2. **Given** обращение с тремя вопросами, **When** отправлено, **Then** создано три подзадачи со своими маршрутами.
3. **Given** открытая заявка по Wi-Fi, **When** тот же пользователь снова пишет о Wi-Fi, **Then** обращение привязано к существующей заявке.
4. **Given** обращение с матом/на английском, **When** отправлено, **Then** обработано: мат замаскирован, для оператора приложен перевод.
5. **Given** гость без почты МИСИС, **When** отправляет обращение, **Then** обращение обработано в полном объёме (гостевая сессия создана, маршрут и реакция выданы).

### User Story 2 - Автодиагностика сервисов университета (Priority: P1)

Пользователь жалуется «сайт не открывается» / «Moodle не грузится» / «Wi-Fi не работает». Агент сам вызывает инструменты проверки: реальные — https://misis.ru и https://newlms.misis.ru; эмулируемые — Wi-Fi сети MISIS-Guest, MISIS-EDU, MISIS-CORP. Если сервисы в норме — задаётся шаблонный уточняющий вопрос, разбор продолжается от ответа. Если сбой подтверждён — мгновенное шаблонное извещение «сбой известен, работы ведутся» без участия модели, заявка фиксируется.

**Why this priority**: Агентная часть кейса: система действует (проверяет), а не только генерирует текст.

**Independent Test**: Жалоба на сайт при живом misis.ru → уточняющий вопрос; переключить Wi-Fi в «сбой» → жалоба на Wi-Fi → шаблонное извещение без вызова модели.

**Acceptance Scenarios**:

1. **Given** misis.ru доступен, **When** жалоба «не открывается сайт», **Then** выполнена проверка, результат «в норме», задан шаблонный уточняющий вопрос.
2. **Given** MISIS-EDU в состоянии «сбой», **When** жалоба на Wi-Fi, **Then** мгновенное шаблонное извещение, заявка сохранена с результатом проверки.
3. **Given** ответ на уточняющий вопрос получен, **When** разбор продолжается, **Then** учтён ответ (новая классификация/маршрут).

### User Story 3 - RAG-агент по документам и шаблонам (Priority: P2)

База знаний состоит из документов (регламенты: заказ справок, пароли, Wi-Fi, Moodle, поддержка) и шаблонов ответов (извещение о сбое, уточняющие вопросы, эскалация, массовый ответ, перенаправление). RAG-агент переформулирует запрос пользователя, при необходимости разделяет его на подзапросы, выполняет поиск по базе и формирует итоговый ответ строго по найденному: документы цитируются, шаблоны заполняются деталями. Пустая выдача или неуверенность — эскалация, а не выдуманный ответ.

**Why this priority**: Закрывает массу типовых обращений без человека; честный ответ жюри «где LLM, а где логика».

**Independent Test**: Вопрос, покрытый документом → ответ по документу; вопрос вне базы → эскалация без выдумки.

**Acceptance Scenarios**:

1. **Given** документ «Регламент Wi-Fi сетей», **When** вопрос «как подключиться к MISIS-EDU», **Then** ответ сформирован по документу.
2. **Given** составной вопрос по двум темам, **When** обрабатывается, **Then** агент разделил запрос и собрал ответ по обеим темам.
3. **Given** вопрос вне базы, **When** обработано, **Then** создана эскалация, пользователю сообщено «передал специалисту».

---

### User Story 4 - Заказ справок как действие агента (Priority: P2)

Авторизованный пользователь просит справку. Агент по документу «Регламент заказа справок» объясняет условия и через инструмент заказа оформляет заявку: данные профиля подставляются автоматически. Каталог: справка о выплатах; справка-вызов; справка для переболевших/медотвода/вакцинации; справка с места учёбы; справка в военкомат. У заказа статусы: «не обработана» → «обрабатывается» → «готова и ждёт выдачи» → «забрана». Статусы видны пользователю; смена статусов — оператором (UI — фича 002).

**Why this priority**: Реальный прикладной сценарий МИСИС, демонстрирует связку RAG + инструмент + профиль пользователя.

**Independent Test**: «Мне нужна справка с места учёбы» → агент нашёл регламент, оформил заказ со статусом «не обработана»; смена статуса оператором видна пользователю.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** заказ справки с места учёбы, **Then** заказ создан с данными профиля и статусом «не обработана».
2. **Given** заказ создан, **When** оператор меняет статус, **Then** пользователь видит актуальный статус из четырёх возможных.

---

### User Story 5 - Эскалация оператору с саммари (Priority: P2)

Когда модель не справляется (нет ответа в базе, неуверенность, тема вне компетенции), обращение эскалируется оператору с пакетом: саммари сути, что уже проверено автоматически и с каким результатом, рекомендуемый следующий шаг, исходный текст/расшифровка, перевод при необходимости. «Помощник оператора» поясняет, почему обращение передано человеку.

**Why this priority**: Оператор — второй ключевой пользователь; безопасный маршрут вместо ошибок модели.

**Independent Test**: Создать эскалацию вопросом вне базы → пакет оператора содержит саммари, проверки, рекомендацию, исходник.

**Acceptance Scenarios**:

1. **Given** эскалированное обращение, **When** оператор открывает его, **Then** видны суть, результаты проверок, рекомендация, исходный текст и перевод (если не на русском).

---

### User Story 6 - Детектор массовых сбоев и массовый ответ (Priority: P3)

Несколько однотипных обращений от разных пользователей → инцидент: экстренное уведомление дежурных (баннер в админке + Telegram) с агрегированным саммари. Новые однотипные обращения при активном инциденте получают шаблонное извещение и привязываются к инциденту без повторного уведомления. Оператор одной кнопкой рассылает массовый ответ всем затронутым (шаблон из базы знаний).

**Why this priority**: Вау-фича демо и реальная ценность раннего обнаружения инцидентов.

**Independent Test**: 3 однотипные жалобы за 15 минут → инцидент + уведомление ≤ 1 мин; кнопка массового ответа рассылает шаблон всем затронутым.

**Acceptance Scenarios**:

1. **Given** два обращения о MISIS-EDU за 15 минут, **When** третье поступает, **Then** инцидент создан, дежурные уведомлены.
2. **Given** активный инцидент, **When** четвёртая жалоба, **Then** шаблонное извещение, привязка к инциденту, без повторного уведомления.
3. **Given** активный инцидент, **When** оператор нажимает «уведомить затронутых», **Then** всем авторам привязанных обращений отправлен массовый ответ.

---

### User Story 7 - Самообучение базы знаний (Priority: P3)

Оператор, закрывая эскалацию, одной кнопкой добавляет решение в базу знаний: LLM готовит черновик статьи по переписке, оператор подтверждает — статья индексируется и доступна RAG-агенту. Система умнеет с каждым обращением.

**Why this priority**: Замкнутый цикл обучения — сильная история для питча, но строится поверх эскалаций и RAG.

**Independent Test**: Закрыть эскалацию → «в базу знаний» → подтвердить черновик → задать аналогичный вопрос → получить ответ из новой статьи.

**Acceptance Scenarios**:

1. **Given** закрытая эскалация, **When** оператор подтверждает черновик статьи, **Then** статья в базе и находится RAG-агентом.

---

### Edge Cases

- Обращение не на русском → перевод для оператора + оригинал.
- Обращение только из мата → нормализуется, обрабатывается, не отклоняется.
- Составное обращение разных категорий → подзадачи по разным маршрутам.
- Сервисы в норме, пользователь настаивает → эскалация с историей переписки.
- Пользователь молчит после уточняющего вопроса → заявка остаётся в «ждёт ответа пользователя», без эскалации и таймаутов.
- Модель недоступна/не уверена → безопасный маршрут: эскалация оператору.
- Инструмент вернул ошибку (сайт не отвечает на проверку) → фиксируется как возможный сбой, маршрут — эскалация/извещение по правилам.
- Агент превысил лимит вызовов инструментов (>3 на обращение) → эскалация оператору с журналом действий.
- Однотипные обращения при активном инциденте → одно уведомление, без спама.
- Общежитие → вне скоупа: вежливое шаблонное перенаправление.
- Заказ справки без авторизации → невозможен: система просит войти.

## Requirements *(mandatory)*

### Functional Requirements

**Приём и нормализация**

- **FR-001**: Система MUST принимать обращение свободным текстом (письмо или расшифровка разговора) от любого посетителя: авторизованного по почте МИСИС (привязка к профилю) или гостя (привязка к гостевой сессии).
- **FR-002**: Система MUST маскировать ненормативную лексику; исходный текст сохраняется и доступен оператору с пометкой.
- **FR-003**: Система MUST определять язык обращения и прикладывать перевод на русский для оператора.
- **FR-004**: Система MUST разбивать составное обращение на атомарные подзадачи.

**Маршрутизация**

- **FR-010**: Система MUST классифицировать каждую подзадачу языковой моделью в маршрут: автопроверка сервиса / база знаний / заказ справки / эскалация оператору.
- **FR-011**: Система MUST присваивать приоритет (критичный/высокий/средний/низкий) с обоснованием: модель предлагает, детерминированные правила могут только повысить (подтверждённый сбой сервиса → критичный; активный инцидент по теме → не ниже высокого); понижение правилами запрещено.
- **FR-012**: Система MUST сохранять и показывать оператору обоснование выбранного маршрута («почему так решено»).
- **FR-013**: Безопасный маршрут: система MUST эскалировать оператору при недоступности модели; при срабатывании детерминированных триггеров-условий (настраиваемый список, напр. жалоба на сотрудника, юридические темы — форсируют маршрут или эскалацию); и при уверенности классификатора ниже настраиваемого порога (`confidence` 0..1, дефолт 0.6).
- **FR-014**: Система MUST дедуплицировать: повторное обращение привязывается к открытой заявке при совпадении сервиса и категории из классификатора (единое правило однотипности, см. FR-050).
- **FR-015**: Система MUST вести жизненный цикл заявки по статусам: «новая» → «в работе» → «ждёт ответа пользователя» → «решена» → «закрыта»; эскалация является маршрутом/признаком заявки, а не статусом.
- **FR-016**: Уровни доступа: без почты МИСИС доступны подача обращений, автопроверки сервисов, ответы базы знаний, извещения о сбоях и уточняющий диалог; с почтой — дополнительно заказ справок, кабинет (история обращений) и персональные статусы заказов. При запросе возможности уровня «почта» без авторизации система MUST предложить авторизоваться и отказать в выполнении действия (реакция `auth_required`; действие не выполняется).

**Инструменты**

- **FR-020**: Система MUST вести реестр инструментов двух типов: `exec` (выполняются без LLM) и `llm` (с участием модели).
- **FR-021**: Агент MUST самостоятельно вызывать инструменты по результату классификации (самовызов), включая повторные вызовы при необходимости; не более 3 вызовов инструментов на обращение — при превышении эскалация оператору с журналом действий.
- **FR-022**: Реальная проверка доступности https://misis.ru (код ответа, время отклика); «доступен» = HTTP 2xx или 3xx в пределах 5 секунд.
- **FR-023**: Реальная проверка доступности https://newlms.misis.ru; «доступен» = HTTP 2xx или 3xx в пределах 5 секунд.
- **FR-024**: Эмулируемое состояние Wi-Fi сетей MISIS-Guest, MISIS-EDU, MISIS-CORP с ручным переключением.
- **FR-025**: Если сервисы в норме — шаблонный уточняющий вопрос и продолжение разбора по ответу; не более 2 раундов уточнений, далее — эскалация оператору с историей переписки. Молчание пользователя не эскалируется: заявка остаётся в статусе «ждёт ответа пользователя».
- **FR-026**: При подтверждённом сбое — мгновенное шаблонное извещение без генерации моделью, заявка фиксируется.

**База знаний (RAG)**

- **FR-030**: База знаний MUST состоять из документов (регламенты) и шаблонов ответов; предварительный состав: регламент заказа справок, политика паролей, регламент Wi-Fi, регламент Moodle, регламент поддержки; шаблоны: извещение о сбое, уточняющие вопросы по категориям, эскалация, массовый ответ, перенаправление вне скоупа.
- **FR-031**: RAG-агент MUST переформулировать запрос, при необходимости разделять на подзапросы, выполнять поиск и формировать итоговый ответ строго по найденному (документы цитируются, шаблоны заполняются деталями).
- **FR-032**: При пустой выдаче или неуверенности система MUST эскалировать, а не генерировать ответ без источника.
- **FR-033**: Структура базы MUST позволять добавление новых статей в рантайме (см. FR-063).

**Справки**

- **FR-040**: Система MUST оформлять заказ справки как действие агента (инструмент заказа) с автоподстановкой данных профиля.
- **FR-041**: Каталог справок MUST включать: справка о выплатах; справка-вызов; справка для переболевших/медотвода/вакцинации; справка с места учёбы; справка в военкомат.
- **FR-042**: Заказ MUST иметь статусы: «не обработана» → «обрабатывается» → «готова и ждёт выдачи» → «забрана»; смена статусов — оператором; пользователь видит актуальный статус.
- **FR-043**: Заказ справки MUST требовать авторизованного пользователя (почта МИСИС); гостю — отказ с предложением авторизоваться (FR-016), заказ не создаётся.

**Массовые сбои**

- **FR-050**: Детекция массового сбоя: ≥3 однотипных обращений (однотипные = совпадение сервиса и категории из классификатора, напр. «Wi-Fi / MISIS-EDU / недоступность») за скользящее окно (по умолчанию 15 минут) → инцидент.
- **FR-051**: При инциденте — экстренное уведомление дежурных (админка + Telegram) с агрегированным саммари.
- **FR-052**: При активном инциденте новые однотипные обращения MUST получать шаблонное извещение и привязываться к инциденту без повторного уведомления.
- **FR-053**: Оператор MUST иметь возможность одной кнопкой разослать массовый ответ всем затронутым инцидентом пользователям.

**Оператор и обучение**

- **FR-060**: Эскалация MUST содержать: саммари сути, результаты автопроверок, рекомендуемый шаг, исходный текст/расшифровку, перевод (при необходимости).
- **FR-061**: Система MUST вести журнал действий по каждому обращению.
- **FR-062**: Система MUST считать метрики: % обращений без человека, среднее время первой реакции, число инцидентов.
- **FR-063**: По закрытии эскалации система MUST уметь готовить LLM-черновик статьи базы знаний; после подтверждения оператором статья индексируется и доступна RAG-агенту.

### Key Entities

- **Пользователь**: профиль (ФИО, группа/роль, email МИСИС), сессия авторизации.
- **Обращение**: текст/расшифровка, канал, язык, автор, время, маскированный и исходный текст.
- **Подзадача**: суть, сервис, категория, маршрут, обоснование маршрута, приоритет, статус.
- **Заявка**: агрегат по обращению — статус (жизненный цикл по FR-015), история, привязка к инциденту, дубли, признак эскалации.
- **Сервис**: название, тип проверки (реальная/эмулируемая), состояние, время последней проверки.
- **Статья базы знаний**: тип (документ/шаблон), заголовок, текст, тема; источник ответов.
- **Заказ справки**: тип (из каталога FR-041), заявитель, статус (FR-042), время.
- **Инцидент**: сервис/тема, число обращений, окно, статус, уведомления, массовый ответ.
- **Эскалация**: обращение + саммари + контекст + статус у оператора.
- **Инструмент**: запись реестра — имя, тип (exec/llm), параметры, результат.
- **Триггер**: настраиваемое условие вида «условие → форсируемый маршрут/эскалация», применяется до/после классификатора.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Первая содержательная реакция (ответ, уточнение или извещение) — не позднее 60 секунд после отправки.
- **SC-002**: ≥ 90% обращений контрольного демо-набора (10 типовых сценариев) маршрутизируются корректно.
- **SC-003**: Оператор понимает ситуацию по эскалации без чтения исходника — ≤ 30 секунд.
- **SC-004**: При подтверждённом сбое извещение выдаётся ≤ 2 секунд (без обращения к модели).
- **SC-005**: Массовый сбой (3 однотипных за 15 минут) детектируется, дежурные уведомлены ≤ 1 минуты после третьего обращения.
- **SC-006**: 100% обращений без ответа в базе уходят оператору; 0 ответов без источника.
- **SC-007**: Заказ справки оформляется end-to-end (запрос → регламент → заказ со статусом) ≤ 60 секунд.
- **SC-008**: Полный демо-цикл «обращение → маршрут → действие → результат» — ≤ 2 минуты.

## Assumptions

- Авторизация эмулируется (вход по email МИСИС без внешнего IdP и реальных паролей); профили тестовые. Домены: `@misis.ru`, `@edu.misis.ru`.
- Пользователь авторизуется на сайте в самом начале работы, до подачи обращений — «по мне была инфа».
- Состав базы знаний — предварительный (FR-030); финальный наполнение утверждается отдельно, добавление статей возможно в рантайме.
- Порог детектора (3/15 мин) — настраиваемый дефолт.
- Wi-Fi-проверки эмулируются; проверки сайта и LMS — реальные HTTP-запросы.
- Общежития — вне скоупа.
- LLM и эмбеддинги предоставляются организаторами (Yandex AI Studio); конкретные модели уточняются на месте.
- Персональные данные в LLM-запросах не ограничиваются: данные и модель — в юрисдикции РФ (Yandex AI Studio), передача профиля в промптах допустима; при смене провайдера правило пересматривается.
- Веб-интерфейс (вход, формы, личный кабинет, админка, тест-панель) — фича 002; Telegram-бот — фича 003. Данная фича — ядро: логика, агент, инструменты, данные.
- Данные хранятся локально; аккаунты реальных пользователей и роли — вне скоупа прототипа.
