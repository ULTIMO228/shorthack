# Feature Specification: Telegram-бот поддержки МИСИС

**Feature Branch**: `[003-telegram-bot]`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "Telegram-бот как канал поддержки МИСИС поверх ядра (фича 001): подача обращений текстом, тот же конвейер обработки, ответы и уточняющий диалог в чате, привязка Telegram-аккаунта к профилю по почте МИСИС («по мне была инфа»), заказ справок и просмотр статусов заказов, уведомления дежурному оператору об инцидентах и эскалациях."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Обращение через бота (Priority: P1)

Пользователь пишет обращение в Telegram-бота свободным текстом (как письмо или рассказ о проблеме). Обращение проходит тот же конвейер ядра (нормализация → сплиттер → классификация → маршрут → действие), ответ приходит в тот же чат: ответ из базы знаний, уточняющий вопрос или извещение о сбое. Обращение видно в админке с пометкой канала «Telegram».

**Why this priority**: Основной сценарий бота; «поддержка в мессенджере» — эффектное демо с телефона.

**Independent Test**: Отправить боту «не работает Wi-Fi» при «сбое» MISIS-EDU → получить извещение в чат; обращение появилось в админке с каналом Telegram.

**Acceptance Scenarios**:

1. **Given** работающий бот, **When** пользователь отправляет обращение, **Then** ответ ядра приходит в тот же чат ≤ 60 секунд.
2. **Given** подтверждённый сбой сервиса, **When** жалоба на этот сервис, **Then** шаблонное извещение приходит мгновенно.

---

### User Story 2 - Привязка профиля по почте МИСИС (Priority: P1)

При первом обращении бот просит привязать аккаунт: пользователь вводит email МИСИС, подтверждает (эмуляция — код/кнопка). Дальше бот знает профиль: обращения и заказы справок привязаны к пользователю — «по мне была инфа», как на сайте.

**Why this priority**: Без привязки невозможны заказ справок, дедупликация и персональные статусы — те же требования, что и у веб-входа.

**Independent Test**: Новый пользователь → бот запросил email → после привязки заказ справки доступен, данные профиля подставляются.

**Acceptance Scenarios**:

1. **Given** непривязанный аккаунт, **When** первое обращение, **Then** бот запрашивает email МИСИС и подтверждение.
2. **Given** привязанный аккаунт, **When** обращение отправлено, **Then** оно привязано к профилю и видно в кабинете на сайте.

---

### User Story 3 - Уточняющий диалог в чате (Priority: P2)

Если ядро задаёт шаблонный уточняющий вопрос, бот ведёт диалог в чате: помнит контекст обращения до его завершения, передаёт ответы в ядро, возвращает продолжение разбора. Пользователь не повторяет проблему заново.

**Why this priority**: Без состояния диалога бот — одноразовая форма; ветка «сервисы в норме → уточнение» — половина сценариев.

**Independent Test**: Жалоба на сайт при живом misis.ru → уточняющий вопрос в чате → ответ пользователя → продолжение разбора без повтора обращения.

**Acceptance Scenarios**:

1. **Given** задан уточняющий вопрос, **When** пользователь отвечает в чат, **Then** ядро продолжает разбор с учётом ответа и контекста.

---

### User Story 4 - Справки через бота (Priority: P2)

Команда `/certs` (или диалоговая кнопка): каталог 5 типов справок, заказ выбранного типа (профиль подставляется), список своих заказов со статусами. Заказ, созданный через бота, виден в кабинете на сайте и в админке оператора.

**Why this priority**: Паритет с веб-кабинетом по прикладному сценарию МИСИС.

**Independent Test**: `/certs` → заказ справки с места учёбы → заказ со статусом «не обработана» виден в боте и на сайте.

**Acceptance Scenarios**:

1. **Given** привязанный аккаунт, **When** заказ справки через бота, **Then** заказ создан с профилем и статусом «не обработана».
2. **Given** есть заказы, **When** `/certs`, **Then** показаны заказы с актуальными статусами.

---

### User Story 5 - Уведомления дежурному (Priority: P3)

Дежурный оператор получает в Telegram: экстренное уведомление об инциденте (агрегированное саммари: сервис, число обращений, период) и уведомление о новой эскалации (саммари сути). Уведомление об инциденте — не позднее минуты после его создания.

**Why this priority**: Закрывает «экстренно передавать кому-то» из заказа; дежурный реагирует без постоянного взгляда в админку.

**Independent Test**: Симулировать волну из 3 жалоб → дежурный получает сообщение с саммари инцидента ≤ 1 мин.

**Acceptance Scenarios**:

1. **Given** создан инцидент, **When** уведомление отправлено, **Then** дежурный получает сообщение с сервисом, числом обращений и периодом.
2. **Given** новая эскалация, **When** она создана, **Then** дежурный получает саммари сути.

---

### Edge Cases

- Сообщение от непривязанного аккаунта, не являющееся email → бот повторяет просьбу о привязке, не теряя текст обращения.
- Пользователь прислал несколько вопросов одним сообщением → ядро разбивает, бот отвечает по каждой подзадаче.
- Бот недоступен в момент ответа ядра → ответ доставляется при восстановлении (очередь исходящих).
- Команды до привязки → работают только `/start` и `/help`, остальное — после привязки.
- Длинный ответ ядра → разбивается на сообщения по лимитам Telegram.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Бот MUST принимать текстовые обращения и передавать их в конвейер ядра (фича 001) без изменений логики.
- **FR-002**: Результат маршрута (ответ / уточнение / извещение о сбое) MUST возвращаться в тот же чат.
- **FR-003**: Бот MUST выполнять привязку аккаунта к профилю по email МИСИС (домены `@misis.ru`/`@edu.misis.ru`) с подтверждением; до привязки доступны только `/start` и `/help`.
- **FR-004**: Обращения из бота MUST быть привязаны к профилю и помечены каналом «Telegram» (видны в админке и кабинете).
- **FR-005**: Бот MUST вести уточняющий диалог с сохранением контекста обращения до его завершения.
- **FR-006**: Бот MUST поддерживать команды: `/start`, `/help`, `/status` (мои обращения), `/certs` (каталог, заказ, мои заказы со статусами).
- **FR-007**: Заказ справки через бота MUST использовать профиль и создавать заказ с начальным статусом «не обработана»; заказ виден во всех каналах.
- **FR-008**: Бот MUST отправлять дежурному: уведомление об инциденте с агрегированным саммари и уведомление о новой эскалации с саммари сути.
- **FR-009**: Извещение о подтверждённом сбое MUST доставляться мгновенно (шаблон, без генерации моделью).

### Key Entities

- **Telegram-аккаунт**: chat id, привязка к профилю, состояние диалога.
- **Дежурный чат**: чат/аккаунт дежурного оператора для уведомлений.
- **Исходящее сообщение**: текст, адресат, статус доставки.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Первая реакция на обращение в чате — ≤ 60 секунд.
- **SC-002**: Сценарий «жалоба на Wi-Fi при сбое → извещение» проходит полностью в боте, без веба.
- **SC-003**: Уведомление дежурному об инциденте — ≤ 1 минуты после создания инцидента.
- **SC-004**: 100% обращений из бота привязаны к профилю и видны в админке с пометкой канала.
- **SC-005**: Уточняющий диалог завершается без повторного описания проблемы пользователем (контекст сохранён в 100% шагов).

## Assumptions

- Бот работает через long polling (локальный прототип, без вебхуков и публичного домена); токен — в `.env`.
- Дежурный — один чат/аккаунт, без ролевой модели.
- Подтверждение привязки email эмулируется (код показывается в интерфейсе/логе или подтверждение кнопкой), без реальной отправки писем.
- Вся логика — в ядре (фича 001); бот — тонкий канал ввода/вывода и уведомлений.
- Веб-кабинет и админка — фича 002; бот с ними согласован по данным (заказы, статусы, обращения).
