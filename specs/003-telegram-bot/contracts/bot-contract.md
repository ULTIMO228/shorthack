# Phase 1 — Контракт бота (003)

Полное описание поведения Telegram-бота: команды, тексты (verbatim), клавиатуры, сценарии, маппинг на REST ядра. Документ самодостаточен для реализации; дополнительно нужен только `specs/001-misis-support-assistant/contracts/api.md` (форматы запросов/ответов ядра).

## 1. Команды

| Команда | Кто может | Ответ бота | Вызовы ядра |
|---|---|---|---|
| `/start` | все | приветствие (T1) + предложение описать проблему; привязка НЕ запускается | `GET /api/internal/tg/link?chat_id=` |
| `/help` | все | справка (T2) | — |
| `/link` | непривязанные | запуск привязки (сценарий S1): запрос email (T3) | `POST /api/internal/tg/link` |
| `/status` | привязанные | список обращений (сценарий S3) | `GET /api/requests` |
| `/certs` | привязанные | каталог справок + мои заказы (сценарий S4) | `GET /api/certs/catalog`, `GET /api/certs/orders` |
| `/cancel` | все | сброс диалога/ввода: state→`idle` | (локально) |
| любой текст | все | обращение (S2) или ответ в диалоге (S2b); непривязанный — как гость | `POST /api/requests`, `POST /api/requests/{id}/reply` |

Непривязанному на `/status`, `/certs` и на реакцию `auth_required` ядра: T16 (просьба привязаться) + отказ в выполнении функции. Привязка предлагается один раз после первого обращения гостя.

## 2. Тексты сообщений (messages.py, константы)

- **T1** (приветствие): «Здравствуйте! Это поддержка НИТУ МИСИС. Опишите проблему своими словами — я разберу обращение и помогу. Команды: /help — что я умею, /status — мои обращения, /certs — справки.»
- **T2** (справка): «Я принимаю обращения текстом: проверяю сервисы университета (сайт, LMS, Wi-Fi), отвечаю по базе знаний, оформляю справки, передаю сложное оператору. Просто напишите, что случилось.»
- **T3** (запрос email): «Привяжем аккаунт, чтобы были доступны справки и статусы. Отправьте корпоративную почту (@misis.ru или @edu.misis.ru):»
- **T16** (нужна привязка): «Эта функция доступна после привязки почты МИСИС. Отправьте /link для привязки — это займёт минуту.»
- **T4** (email ок): «На {email} отправлен код подтверждения. Введите его:» (демо: код показывает оператор)
- **T5** (email плохой): «Это не корпоративная почта МИСИС. Нужен адрес на @misis.ru или @edu.misis.ru:»
- **T6** (код ок): «Готово, {full_name}! Аккаунт привязан. Опишите вашу проблему.»
- **T7** (код неверный): «Код не подходит (осталось попыток: {n}). Проверьте и введите ещё раз:»
- **T8** (код исчерпан): «Попытки кончились. Отправьте почту ещё раз — вышлем новый код.»
- **T9** (обращение принято, работа агента): «Принял, разбираю… (обычно до минуты)»
- **T10** (извещение о сбое): «🔴 {text}» — текст от ядра как есть; плашка-эквивалент: сообщение начинается с 🔴
- **T11** (эскалация): «Передал специалисту поддержки. Номер заявки: {number}. Ответим здесь же.»
- **T12** (нет обращений): «У вас пока нет обращений.»
- **T13** (ошибка ядра/сети): «Сервис временно недоступен, попробуйте через пару минут. Обращение не потеряно.»
- **T14** (заказ создан): «✅ Заказ №{id}: {title}. Статус: {status}. Смотреть заказы: /certs»
- **T15** (общежитие/вне скоупа — приходит от ядра как answer, бот не фильтрует) — ретрансляция как есть.

Все тексты правятся только в `messages.py`. Ядро всегда возвращает тексты реакций по-русски — бот их НЕ переписывает, только оборачивает (T9-T11, T14).

## 3. Клавиатуры (keyboards.py, inline)

- **K1** (каталог справок, по данным `GET /api/certs/catalog`): по одной кнопке на тип, `callback_data="cert:<type>"`; + кнопка «Мои заказы» → `callback_data="cert:my"`.
- **K2** (подтверждение заказа): [«✅ Заказать» — `cert_order:<type>`] [«Отмена» — `noop`].
- **K3** (под обращением с реакцией clarification): кнопок нет — ждём текст. Ничего не рисуем.
- На все `callback_query` — обязательный `answerCallbackQuery` (иначе «часики» у пользователя); на `noop` — пустой ack.

## 4. Сценарии

### S1. Привязка аккаунта (FR-003, опциональная)
Запуск: команда `/link`, или переход из T16 (пользователь запросил `/certs`/`/status` без привязки), или из предложения бота после первого гостевого обращения. Обращения привязка НЕ блокирует.
1. Запуск → T3, state=`awaiting_email`.
2. Текст похож на email с доменом из белого списка → `POST /api/internal/tg/link {chat_id, email}` → T4, state=`awaiting_confirm`. Домен не из списка → T5 (state не меняется). Не email вовсе → T5.
3. Ввод кода → `POST /api/internal/tg/link/confirm {chat_id, code}`:
   - 200 `{ok:true, user}` → T6 с `user.full_name`, state=`idle`; создать сессию ядра: `POST /api/auth/login {email}` (cookie храним в `core_api` клиенте этого chat_id).
   - код неверный → T7 (счётчик в tg_links на стороне ядра; 3 неверных → ядро возвращает `{"ok": false, "reason": "attempts_exceeded"}` → T8, state=`awaiting_email`).

### S2. Обращение (FR-001, FR-002, FR-009)
1. Текст в state=`idle` (привязанный или гость) → сразу T9 (мгновенный фидбек), затем `POST /api/requests {"text": "...", "channel": "telegram"}`. Гость: запрос без пользовательской сессии — ядро создаёт гостевую (FR-016); обращение помечается гостевым.
2. Ответ ядра: для каждой реакции — своё сообщение:
   - `outage_notice` → T10; тикет фиксируется, state остаётся `idle`.
   - `clarification` → текст вопроса + state=`dialog:<request_id>`.
   - `answer` → текст ответа как есть (+ если `subtasks[].route="kb"` — ничего дополнительно).
   - `cert_ordered` → T14 (id, title, status из реакции).
   - `escalated` → T11 с `ticket.number`.
   - `auth_required` → T16 (функция требует привязки; действие не выполнено).
   - `duplicate=true` → префикс: «Это похоже на вашу заявку {number} — дополнил её.» далее реакции как обычно.
3. Подзадач несколько → реакции приходят массивом; бот шлёт по одному сообщению на подзадачу с префиксом «{i}/{n}:».

### S2b. Диалог уточнения (FR-005)
- state=`dialog:<request_id>`, любой текст → `POST /api/requests/{id}/reply {"text": ...}` → обработка реакций как в S2.2; не-clarification → state=`idle`. 409 от ядра → state=`idle` + «Диалог по обращению завершён. Опишите проблему заново, если нужно.»

### S3. /status — мои обращения (FR-006)
`GET /api/requests` → пусто: T12. Иначе до 10 строк: `{number} · {дата ДД.ММ ЧЧ:ММ} · {status} · {summary первой подзадачи}`. Если есть активный инцидент по теме — ядро помечает в ответе, бот добавляет строку «🔴 По этой теме объявлен инцидент».

### S4. /certs — справки (FR-006, FR-007)
1. `GET /api/certs/catalog` + `GET /api/certs/orders`.
2. Сообщение 1: «Заказ справки:» + K1 (типы).
3. Сообщение 2: «Ваши заказы:» + строки `№{id} · {title} · {status}` (или «заказов нет»).
4. `callback_data="cert:<type>"` → K2 с названием; `cert_order:<type>` → `POST /api/certs/orders {"cert_type": type}` → T14 (editMessageText в то же сообщение); `cert:my` → перерисовать сообщение 2 актуальными статусами.

### S5. Уведомления дежурному (FR-008)
Цикл каждые 10 c: `GET /api/internal/outbound?status=pending` (заголовок `X-Bot-Token`) → каждое сообщение → `sendMessage(chat_id из записи)` → `POST /api/internal/outbound/{id}/ack {"status":"sent"}`. Ошибка отправки → ack `failed` + лог в консоль бота. Тексты формирует ядро (инцидент: «🔴 Инцидент: …», эскалация: «👤 Эскалация {number}: …») — бот не изменяет.

## 5. Обработка ошибок и границы

- Ядро недоступно/5xx/таймаут → T13; обращение НЕ ретраим автоматически (чтобы не плодить дубли — дедупликация на стороне ядра всё равно склеит, но заявлять это не будем); сообщение об ошибке достаточно.
- Telegram 429 → сон `retry_after`; сетевые ошибки → backoff R2 (research.md).
- Сообщение пользователя >3500 символов → передаём ядру как есть (ядро принимает Text); ответы ядра >4096 → разбиение в `tg.py` по абзацам, суффикс «(продолжение)».
- Фото/голос/файлы → «Я работаю только с текстом. Опишите проблему словами.» (без вызова ядра).
- Группы: бот отвечает только в личке; в группах — молчание (проверка `chat.type == "private"`).
- Рестарт бота: offset из `.bot_offset`; сессии ядра пересоздаются по tg_links прозрачно при первом обращении.

## 6. Приёмочный чек-лист для разработчика 003

1. `/start` у нового пользователя → T1 (без запуска привязки); `/link` → полный цикл привязки (T3→T6).
2. Гость без привязки: обращение обработано полностью; `/certs` и `/status` → T16 + отказ; попытка заказать справку через диалог → `auth_required` → T16.
2. «не работает wifi» при «сбое» MISIS-EDU → 🔴 извещение ≤ 2 c после ответа ядра (SC-004 ядра).
3. Уточняющий диалог: 2 сообщения туда-обратно без повторного описания (SC-005).
4. `/certs` → заказ справки с места учёбы кнопками → T14; заказ виден в админке 002.
5. `/status` → строки с номерами SUP-2026-*.
6. `simulate_wave` из админки 002 → дежурному сообщение ≤ 1 мин (SC-003).
7. Выключить ядро на 30 c → T13; включить → бот продолжает работать без рестарта.
